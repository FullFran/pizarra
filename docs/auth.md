# Authentication

The pizarra gateway protects everything the whiteboard serves — the MCP endpoint (`/mcp`), the canvas page and its assets, the REST API (`/api/*`) and the WebSocket — with OAuth 2.1. You sign in with GitHub, and only the GitHub accounts you list get in. There are no local passwords.

## Topology

The canvas itself is the unmodified [`mcp-excalidraw-server`](https://github.com/yctimlin/mcp_excalidraw) (pinned to the upstream commit in `upstream.json`, see the README), which has no authentication. The gateway starts it as a child process listening **only on `127.0.0.1`** on an internal port (`CANVAS_INTERNAL_PORT`, a free port by default, `3100` in the image), with none of the gateway's auth settings in its environment (it only gets its own data directory), restarts it if it crashes, and stops it on exit. The gateway is the only public listener: it answers `/oauth/*`, the metadata documents, `/mcp` and `/health` itself, and reverse-proxies everything else (the canvas UI, `/api/*` and the WebSocket) to the canvas **after** authentication. The browser's cookie and `Authorization` header are not forwarded to the canvas, and cookies the canvas might set are dropped. Paths with dot segments, backslashes or encoded `.`/`/`/`\` are refused with `400` before proxying.

The auth code is its own bounded context (`src/auth/`): it knows nothing about the canvas or the proxy, the protected resources it issues tokens for are configuration (today one: `${PUBLIC_BASE_URL}/mcp`), and the gateway asks it one question through a port: *is this request authenticated, and as whom?*

No secret has to be configured: GitHub sign-in uses GitHub's [OAuth device flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#device-flow), which needs only the app's public client ID, and the session-signing secret is generated by the server on first start and kept in its data directory.

## When authentication is on

| Bind (`HOST`) | `AUTH_MODE` | Result |
|---|---|---|
| loopback (`127.0.0.1`, the default; `localhost`, `::1`) | unset | **Off.** Local `127.0.0.1` use stays zero-config. |
| any | `oauth` | **On.** Startup fails if a required variable is missing, and the error names it. |
| non-loopback (`0.0.0.0`, `::`, a LAN address) | unset | **On**, same rules as `oauth`. |
| non-loopback | `off` | **Refused** unless `ALLOW_INSECURE_NO_AUTH=true` is also set. |

`ALLOW_INSECURE_NO_AUTH=true` is dangerous: anyone who can reach the address can read and change the canvas and call every MCP tool. Use it only when another layer (a VPN-only network, an authenticating proxy) checks every request.

On a loopback bind, GitHub or auth variables without `AUTH_MODE=oauth` are ignored, so a stray `GITHUB_CLIENT_ID` in your shell never locks you out of a local canvas.

> **Docker:** the image sets `HOST=0.0.0.0`, so it needs either the variables below or `AUTH_MODE=off` with `ALLOW_INSECURE_NO_AUTH=true` (for example when only `-p 127.0.0.1:3000:3000` publishes the port).

## Environment variables

| Variable | Required when on | Meaning |
|---|---|---|
| `AUTH_MODE` | – | `oauth` or `off`. See the table above. |
| `PUBLIC_BASE_URL` | yes | Public origin, e.g. `https://board.example.com`. Must be `https` (plain `http` only for `127.0.0.1`/`localhost`) and must not have a path. It is the OAuth issuer; the protected resource is `${PUBLIC_BASE_URL}/mcp`. |
| `GITHUB_CLIENT_ID` | yes | Client ID of your GitHub OAuth app (public; not a secret). |
| `ALLOWED_GITHUB_LOGINS` | yes | Comma-separated GitHub logins allowed to sign in, case-insensitive, e.g. `FullFran`. **There is no default**: if it is unset the server refuses to start, so nobody gets in by accident. |
| `EXCALIDRAW_DATA_DIR` | yes | Data directory. Tokens and registered clients are kept in `auth-store.json` there, and the generated signing secret in `auth-secret` (both mode `0600`), with the fork's names and format. It also turns on durable canvas state, in `canvas/` below it (see `CANVAS_DATA_DIR`). |
| `CANVAS_DATA_DIR` | no | Where the canvas keeps its durable state (upstream's `EXCALIDRAW_DATA_DIR`). Default `$EXCALIDRAW_DATA_DIR/canvas`. The fork kept `canvas-state-v1.json` and `blobs/` at the data directory's root: move them into `canvas/`, or set `CANVAS_DATA_DIR` to the root, to keep a fork-era drawing. |
| `EXCALIDRAW_EXPORT_DIR` | no | The only directory upstream's MCP file tools may read and write. Default `$EXCALIDRAW_DATA_DIR/files` (upstream's own default is the working directory, i.e. the application). |
| `GITHUB_APP_NAME` | no | The name you gave the GitHub OAuth app. The sign-in page shows it, so you can check GitHub names the same app. |
| `AUTH_SECRET` or `AUTH_SECRET_FILE` | no | Signing secret for session cookies, the sign-in binding cookie and consent forms, at least 32 characters. When neither is set, the server generates one (48 random bytes) in `$EXCALIDRAW_DATA_DIR/auth-secret` on first start and reuses it afterwards. An explicit value wins. Changing or deleting it signs everyone out. |
| `TRUST_PROXY` | behind a proxy | Set it (e.g. `loopback`) when a reverse proxy you control terminates TLS, so rate limits see client IPs. |
| `AUTH_ACCESS_TOKEN_TTL_SECONDS` | no | Access token lifetime. Default `3600` (1 h), 1–86400. |
| `AUTH_REFRESH_TOKEN_TTL_SECONDS` | no | Refresh token lifetime. Default 30 days. |
| `AUTH_SESSION_TTL_SECONDS` | no | Browser session lifetime. Default 7 days. |
| `CANVAS_INTERNAL_PORT` | no | Loopback port of the upstream canvas inside the gateway's host or container. Default: a free port (`3100` in the image). |
| `PIZARRA_ROLE` | no | `gateway` (default) or `canvas`. `canvas` runs only the upstream canvas (on `CANVAS_BIND_HOST:CANVAS_INTERNAL_PORT`, with `<data>/canvas`), for gateways in other containers; it has no auth of its own, so reach it only from a private network. |
| `CANVAS_URL` | no | `http://host:port` of a canvas run with `PIZARRA_ROLE=canvas`. The gateway then spawns no canvas and its `/health` follows that canvas. Several gateways can share one canvas this way. |
| `CANVAS_BIND_HOST` | no | Where the `canvas` role listens. Default `0.0.0.0`. |
| `GITHUB_OAUTH_BASE_URL` / `GITHUB_API_BASE_URL` | no | Override `https://github.com` / `https://api.github.com` (GitHub Enterprise, or a fake GitHub in tests). |

`GITHUB_CLIENT_SECRET` and `GITHUB_CLIENT_SECRET_FILE` are no longer used. If one is still set, the server starts and logs a warning; remove it.

The generated `auth-secret` file is checked on every start: if it is readable by group or others, or shorter than 32 characters, the server refuses to start and says how to fix it (`chmod 600`, or delete it to generate a new one). It is created atomically (written to a temporary `0600` file, then linked into place), so two starts never overwrite each other's secret. Back up the data directory as a whole: losing `auth-secret` only signs browsers out, since tokens are stored separately.

## Create the GitHub OAuth app

1. GitHub → Settings → Developer settings → **OAuth Apps** → **New OAuth App**.
2. **Application name:** something you will recognise on GitHub's confirmation screen, e.g. `Pizarra FullFran`. Put the same name in `GITHUB_APP_NAME`.
3. **Homepage URL:** your `PUBLIC_BASE_URL`, e.g. `https://board.example.com`.
4. **Authorization callback URL:** GitHub requires one, but the device flow never uses it; enter `PUBLIC_BASE_URL` again.
5. Create it, then tick **Enable Device Flow** on the app's page and save.
6. Put the **Client ID** in `GITHUB_CLIENT_ID`. Do **not** generate a client secret: none is needed.

The server asks GitHub for the `read:user` scope, the narrowest one that reads the profile. It only reads the login of whoever signed in and throws GitHub's token away right after; that token is never stored, logged or sent to the browser.

Example (nothing secret in it; the signing secret is generated in `/var/lib/excalidraw`):

```bash
HOST=127.0.0.1 PORT=3000 TRUST_PROXY=loopback \
PUBLIC_BASE_URL=https://board.example.com \
AUTH_MODE=oauth \
GITHUB_CLIENT_ID=Ov23xxxxxxxxxxxx GITHUB_APP_NAME="Pizarra FullFran" \
ALLOWED_GITHUB_LOGINS=FullFran \
EXCALIDRAW_DATA_DIR=/var/lib/excalidraw \
node dist/main.js
```

In a container, mount `EXCALIDRAW_DATA_DIR` on a persistent volume so the generated secret, tokens and canvas survive redeploys; there is no secret to put in the deployment's environment.

**Zero-downtime deploys.** Run the canvas as its own container (`PIZARRA_ROLE=canvas`, one copy, replaced stop-then-start) and the gateway with `CANVAS_URL` pointing at it, both on the same data volume. Gateways then hold no state of their own: sessions are signed cookies, and everything else (clients, tokens, codes, consent tickets, device logins) is in `auth-store.json`, shared safely between copies. A new gateway can start next to the old one and take over once healthy. Never run two canvas copies on one data directory: each keeps the canvas in memory and the last to write would win.

## Signing in

1. Any protected page without a session sends you to `/oauth/login`, which shows a **Sign in with GitHub** button.
2. The button asks GitHub for a device code and shows it on `/oauth/device`, with a link to `https://github.com/login/device`, the app name GitHub will show, and the warning *Only enter this code if you started this sign-in on this screen just now*.
3. You open the link, type the code and authorize the app on GitHub.
4. The page checks with the server every few seconds (at GitHub's `interval`, longer after a `slow_down`). When GitHub confirms, the server reads your login, checks `ALLOWED_GITHUB_LOGINS`, sets the session cookie and takes you back where you were — for an MCP client, the pending `/oauth/authorize` consent page.

If the code expires (GitHub's `expires_in`, at most 15 minutes), you cancel on GitHub, or the account is not allowed, the page says so and offers to start again; no session is created. Without JavaScript, the **I have entered the code** button does the same check.

## What is protected, and how

| Surface | Without credentials | Accepted credentials |
|---|---|---|
| `/mcp` | `401` with `WWW-Authenticate: Bearer resource_metadata="${PUBLIC_BASE_URL}/.well-known/oauth-protected-resource", scope="whiteboard"` | `Authorization: Bearer <access token>` for resource `${PUBLIC_BASE_URL}/mcp` with scope `whiteboard` |
| canvas page, static files | `302` to `/oauth/login` | session cookie |
| `/api/*` | `401` | session cookie, or a bearer access token. Writes with the cookie must come from `PUBLIC_BASE_URL` (`Origin`, or `Referer` when there is no `Origin`), otherwise `403`. |
| WebSocket | `401` | bearer access token, or the session cookie with `Origin` equal to `PUBLIC_BASE_URL` (any other Origin: `403`) |
| `/health` | open | answers only `{"status":"healthy","service":"pizarra"}` — no counts, no pid; `503` with `"status":"unhealthy"` while the canvas is down |

Path matching is case-insensitive (`/API/elements` is `/api/…`), as Express routes it. MCP tools called over `/mcp` run inside the gateway and talk to the canvas directly on `127.0.0.1`, so their writes are what the proxied REST API and WebSocket show.

## Endpoints

| Path | Purpose |
|---|---|
| `/.well-known/oauth-protected-resource` (also `/…/mcp`) | RFC 9728 protected resource metadata |
| `/.well-known/oauth-authorization-server` | RFC 8414 authorization server metadata |
| `/oauth/register` | RFC 7591 Dynamic Client Registration (public or `client_secret_post`/`client_secret_basic` clients) |
| `/oauth/authorize` | Authorization code + PKCE `S256` only. Shows a consent page with the client's name, ID and redirect host. |
| `/oauth/token` | `authorization_code` and `refresh_token` grants |
| `/oauth/login` | Sign-in page (`GET`); `POST` from the same origin starts a GitHub device login |
| `/oauth/device`, `/oauth/device/poll`, `/oauth/device.js` | The code page, its same-origin status check, and the script that polls it |
| `/oauth/logout` | `POST` from the same origin clears the session cookie |

Protocol details:

- **PKCE** is mandatory and only `S256` is accepted; `plain` or a missing challenge is rejected with `invalid_request`.
- **RFC 9207:** every authorization response, success or error, carries `iss=${PUBLIC_BASE_URL}`.
- **RFC 8707:** `resource` is optional; when given it must be `${PUBLIC_BASE_URL}/mcp` (`invalid_target` otherwise). Every token is bound to that resource and checked on every request.
- **Codes** live 60 s, are single use, and are burnt on the first presentation whatever the outcome. Presenting a used code again revokes the tokens it produced.
- **Refresh tokens rotate.** Each one works once; reusing an old one revokes its whole family (every access and refresh token descending from the same authorization code).
- **Clients** are either a Client ID Metadata Document URL (the 2025-11-25 / 2026-07-28 way; `client_id` is an `https` URL with a path whose JSON document lists `redirect_uris`) or a client registered through `/oauth/register`. Metadata documents are fetched only over `https`, only from public IP addresses (loopback, private, link-local, CGNAT, multicast and IPv4-mapped forms are refused, and the connection is pinned to the checked address), without redirects, within 5 s and 64 KiB, and cached for its `Cache-Control: max-age` between 1 minute and 24 hours. Only public clients (`token_endpoint_auth_method: "none"`) are accepted from a document.
- **Redirect URIs** must be registered exactly. Allowed forms: any `https` URI (including `https://chatgpt.com/connector_platform_oauth_redirect`) and `http://127.0.0.1`, `http://localhost` or `http://[::1]` for CLI agents. For those loopback URIs the port may differ from the registered one (RFC 8252 §7.3); scheme, host, path and query must match.
- **Storage:** access and refresh tokens are 256-bit random strings; only their SHA-256 hashes are written, with client secrets also hashed, to `auth-store.json` (`0600`, written atomically). Authorization codes (hashed), used consent tickets and pending device logins live in the same file, so several gateways can share one data volume (two run at once during a blue-green deploy): reads re-load the file when it changed, every change runs under a lock directory next to it (`auth-store.json.lock`, broken after 10 s if its holder died), and single-use checks (codes, refresh tokens, consent tickets) are decided inside that lock, so only one gateway can win them. GitHub's device code is never written: it travels AES-256-GCM sealed in the sign-in binding cookie.
- **Consent tickets** (the approve/deny form) are signed, bound to the session, live 10 minutes and are single use: a second submission of the same form is refused.
- **Rate limits** (per client IP, in memory): `/oauth/token` 60/min, `/oauth/register` 10/min, starting a device login (`POST /oauth/login`) 5/min, the login and code pages 20/min, the device status check 60/min, `/oauth/authorize` 60/min. At most 20 device logins wait for GitHub at once. DCR is capped at 200 registered clients.

## Connecting clients

In every case the client discovers the authorization server from the `401` on `/mcp`, opens a browser on `/oauth/authorize`, you sign in with GitHub (first time only, then the session cookie remembers you), and you approve on the consent page.

**ChatGPT** (connectors / developer mode): add a custom connector with the MCP server URL `https://board.example.com/mcp` and authentication **OAuth**. ChatGPT registers itself through `/oauth/register` with the redirect `https://chatgpt.com/connector_platform_oauth_redirect`.

**Claude Code:**

```bash
claude mcp add --transport http excalidraw https://board.example.com/mcp
# then, inside Claude Code: /mcp → excalidraw → Authenticate
```

**Codex CLI:**

```toml
# ~/.codex/config.toml
[mcp_servers.excalidraw]
url = "https://board.example.com/mcp"
```

```bash
codex mcp login excalidraw
```

Both CLIs use a loopback redirect (`http://localhost:<port>/…` or `http://127.0.0.1:<port>/…`), which is allowed.

**The canvas in a browser (or an iPad):** open `https://board.example.com/`, press **Sign in with GitHub**, enter the code shown on GitHub (on the same device or another one), and the page continues to the canvas by itself.

Client flags change between versions; check each client's own documentation if a command above differs.

## Threat model

Defended against:

- **Anyone on the internet** reaching the server: every surface except `/health` and the OAuth endpoints needs a GitHub login from the allowlist or a token issued after one.
- **Other GitHub users:** they can complete GitHub's login, but get no session and no token.
- **Device-code phishing.** The device flow's known weakness: an attacker starts a sign-in on *their* browser and talks you into typing *their* code on GitHub, which would sign *their* browser in as you. Mitigations:
  - Only accounts in `ALLOWED_GITHUB_LOGINS` can be phished into anything; anyone else gets no session.
  - The page that shows a code says, prominently: *Only enter this code if you started this sign-in on this screen just now*, and names the GitHub app to expect (`GITHUB_APP_NAME`). GitHub's own confirmation screen also names the app.
  - Codes are short-lived: GitHub's `expires_in`, capped at 15 minutes.
  - Each device login is bound to the browser that started it: a random nonce and the device code, AES-256-GCM sealed (the browser cannot read it), in an `HttpOnly`, `SameSite=Strict` cookie; the rest of the login is in the shared auth store and the device code is never written to disk. Only that browser can see the code, poll and receive the session; another browser, a missing or tampered cookie, or a request from another origin gets nothing. Leaking or guessing a code shown on someone else's screen is therefore useless.
  - Starting a device login is same-origin only (`POST` with an `Origin` check), rate limited to 5 per minute per IP, and at most 20 can be pending at once.
  - Residual risk: if you do type a code someone else sent you and approve the named app on GitHub, their browser gets your session. Never enter a code you did not just see on your own screen.
- **Stolen or replayed codes:** PKCE `S256`, exact redirect matching, 60 s single-use codes, replay revokes the issued tokens.
- **Leaked refresh tokens:** rotation with family revocation on reuse; short-lived access tokens.
- **Token confusion:** tokens are bound to `${PUBLIC_BASE_URL}/mcp` and refused anywhere else; RFC 9207 `iss` lets clients detect mix-up attacks.
- **CSRF and cross-site WebSocket hijacking:** `SameSite=Lax` session cookie, an `Origin` check on every cookie-authenticated write whatever its path (paths are matched case-insensitively, as Express routes them, so `/API/…` gets the same rules as `/api/…`), on the consent form, the device login and the WebSocket; single-use consent tickets bound to the session.
- **Clickjacking of the consent page:** `X-Frame-Options: DENY` and `frame-ancestors 'none'`.
- **SSRF through client metadata URLs:** https only, public addresses only, pinned connection, no redirects, size and time limits.
- **Store disclosure:** the store holds only hashes; a copy of it does not grant access.

Assumptions:

- TLS is terminated by a reverse proxy you control, and `PUBLIC_BASE_URL` is the URL people actually use. Set `TRUST_PROXY` only for that proxy.
- The data directory is private to the server's user: it holds the signing secret (`auth-secret`, `0600`) and the token store. There is no GitHub client secret.
- One gateway owns the data directory. Run a single replica. The canvas holds a lock on its directory; when the canvas was killed hard (for example `docker kill`), the gateway removes the lock left behind if its owner process is gone, before starting a new canvas (inside a fresh container the new canvas would otherwise get the dead one's pid and refuse to start).
- Nothing else untrusted runs on the same host or in the same container: the canvas port on `127.0.0.1` has no authentication of its own. In the image only the gateway and the canvas run.

Out of scope:

- Users or roles beyond the allowlist: every allowed login has full access to the canvas.
- Revoking one client from a UI. To revoke everything, stop the server and delete `auth-store.json`; to sign every browser out, change `AUTH_SECRET` or delete the generated `auth-secret`; to drop a person, remove their login from `ALLOWED_GITHUB_LOGINS` and restart (their sessions and tokens stop working).
- Token introspection and revocation endpoints (RFC 7662 / 7009), `private_key_jwt` clients, OpenID Connect.
- Rate limiting shared across processes, and protection against volumetric denial of service (use the proxy). In particular, someone who can reach the server from 4 or more IPs can fill the 20 pending device logins and delay sign-ins for up to 15 minutes (restarting the server clears them; existing sessions and tokens keep working).
- Upstream's CLI (`excalidraw-canvas …`) and stdio MCP server talking to a *remote* pizarra: they send no token. Use `/mcp` for remote agents.
- With auth off on a local machine, the internal canvas port (like any local web server) is reachable by other local processes; only `/mcp` has the DNS-rebinding guard.
