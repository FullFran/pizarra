# Feature: multiuser
Objective: several boards (one upstream canvas per open board), people and agents let in by pluggable auth providers (GitHub, trusted issuers such as Hagalink Projects), invites with editor/viewer roles, embeddable boards.
Branch: `feat/multiuser-pluggable-auth` (worktree `pizarra-multiuser`). Delivery: work-unit commits; push, PR and deploy are Fran's call. Runner: `npm test` (build, node:test units, `scripts/check-*.mjs` wire checks).

## Specs

- S1 (#11) Boards and canvas pool: `boards.json` in /data (id, name, owner, members) under the cross-process lock; one upstream child per open board on its own internal port and `<data>/boards/<id>/canvas`, started on first use, stopped after N idle minutes, capped; `/b/<id>/...` (UI, REST, WebSocket) routed to that child; per-board MCP `/b/<id>/mcp` with one RFC 8707 resource per board; per-board export directory; today's canvas migrates to board `main` and `/mcp` stays its alias. Acceptance: "Two boards open at once; drawing on one never shows on the other (browser and MCP)", "A token for board A is rejected on `/b/B/mcp`", "An idle board stops and reopens with its elements intact", "Existing `pizarra.fullfran.com` canvas and agent tokens keep working after the migration", "Memory per open board measured and written in the doc".
- S2 Pluggable auth (Fran, verbatim): "pues manda un agente en pizarra para que haga toda la parte de multiusuario y que se pueda cambiar el auth como plugin por el auth de otros (en este caso el de hagalink)". An identity/auth provider port; adapters (a) GitHub device flow / OAuth 2.1 (default, unchanged) and (b) trusted-issuer signed tickets (#12, Hagalink first); providers enabled by configuration only (`AUTH_PROVIDERS=github,trusted-issuer`); another org's auth later = one adapter, no core changes; docs/auth.md explains how to write an adapter.
- S3 (#12) Signed board tickets: `TRUSTED_ISSUERS` (issuer id, JWKS URL or pinned keys, EdDSA or ES256, never HS*); claims `iss`, `aud=<pizarra base URL>`, `sub`, `name`, `board`, `role` (`editor`|`viewer`), `jti`, `exp` (at most 5 minutes); browser `GET /b/<id>/enter?ticket=…` single use through `claimOnce`, board-scoped session cookie, redirect to the board, ticket never logged; agents `Authorization: Bearer <ticket>` on `/b/<id>/mcp`, reusable until it expires; a board created through a ticket is owned by its issuer and only that issuer's tickets open it. Acceptance: "Wrong signature, wrong `aud`, expired, reused (browser) or other-board tickets are rejected", "An HS256 ticket is rejected even if it is otherwise valid", "A ticket from issuer X never opens a board owned by issuer Y or by a GitHub user", "The GitHub sign-in flow is unchanged (existing auth checks pass)", "`docs/auth.md` documents the issuer config and the claims".
- S4 (#13) Embeddable boards: `FRAME_ANCESTORS` origin list; board pages send `Content-Security-Policy: frame-ancestors <list>` and no `X-Frame-Options`; auth and consent pages always `DENY`; `SameSite=Lax` kept, embedder must be same-site (documented); `?embed=1` hides pizarra's chrome. Acceptance: "With `FRAME_ANCESTORS` empty, every page still refuses framing (regression check)", "A listed origin can frame a board; an unlisted origin cannot", "Consent and sign-in pages refuse framing even from a listed origin", "`docs/auth.md` explains the same-site requirement".
- S5 (#10 decisions + #5 invites). Defaults taken 2026-11-05 "by default, overridable" (delegated by Fran): (1) viewer role in the first version, with the write filter on REST methods and WebSocket messages; (2) invites by GitHub login only, for GitHub boards; no link invites; issuer boards get no invites; (3) only admins (`ALLOWED_GITHUB_LOGINS`) create GitHub boards; a trusted issuer creates its own board on its first valid ticket. Then #5: invite people to a board as editors and viewers. Out of scope: #6 notebook, #7 embedded pifran.

## Log

- L1 (2026-11-05, Fran, verbatim): "pues manda un agente en pizarra para que haga toda la parte de multiusuario y que se pueda cambiar el auth como plugin por el auth de otros (en este caso el de hagalink)"
- L2 (2026-11-05): Baseline 9484ee7: `npm test` green (unit 50, auth 41 groups, MCP 9, proxy 11). Findings that shape the design: the upstream frontend uses absolute paths (`/assets/...` in index.html and Vite's preload helper `"/"+dep`, `fetch("/api/...")`, WebSocket at `ws(s)://host/`); upstream MCP tools read `EXPRESS_SERVER_URL` and `EXCALIDRAW_EXPORT_DIR` once at import (module constants) and keep `sceneState` at module level; the upstream WebSocket server has no `message` handler (clients never write over it).
- L3 (2026-11-05, T3/T4): Per-board MCP: upstream's config module is a constant snapshot of env at import, so each board imports its own copy of upstream's `dist/` modules via a `node:module` `register` resolve hook that propagates `?pizarra-board=<id>` from parent to child URLs inside the package (third-party packages stay shared); imports are serialized and env is set just before each. Board page: upstream's `index.html` gets `/__pizarra/board.js` first in `<head>`, which rewrites same-origin `fetch('/api/...')` and the root WebSocket to `/b/<id>/...`; `/assets/*` stays unprefixed and shared (Vite's preload helper builds `"/"+dep`). The pool front treats unprefixed paths as main, so the old single-canvas URL contract holds and older gateways keep working against a new canvas container. Upstream's WebSocket server has no message handler, so dropping a viewer's data frames cannot be observed on the wire; the frame filter is unit-tested and the wire check proves the connection keeps working (ping/pong, broadcasts) and the board is unchanged. Memory (Node 24, glibc): canvas ~124 MiB RSS / ~77 MiB PSS per open board; gateway +8.5 MiB per board whose MCP was used.
- L4 (2026-11-05, T6): one full `npm test` run failed in check-auth's in-process group "positive control: same resource accepts the token (expected 200, got 401)"; three reruns of check-auth alone passed 41/41. That check mints a token with `AUTH_ACCESS_TOKEN_TTL_SECONDS`-like TTL 1 s at second granularity (expiresAt = floor(now)+1), so a mint just before a second boundary leaves almost no validity: pre-existing flake in the baseline check, not changed here.
- L5 (2026-11-05): Independent verifier blocker: a UTF-8 BOM before a viewer's JSON-RPC body made the viewer filter's `JSON.parse` throw and pass the request on, while the MCP SDK (WHATWG decode, BOM stripped) ran the tool. RED: check-tickets "a viewer's BOM-prefixed create_element is refused (got 200 ... Element created successfully!)", check-boards same for an invited GitHub viewer. Fix: `viewerRequestVerdict` decodes like the handler (fatal UTF-8, BOM dropped) and fails closed: unreadable JSON, non-object messages, a non-UTF-8 charset or any content encoding are refused (400/415), and the `mcp-name` header is checked too. GREEN: npm test all green (unit 71, auth 41, MCP 9, proxy 11, boards 5, tickets 4, embed 3); an editor's BOM body still writes.
